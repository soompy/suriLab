# AI Agent를 실제 프로젝트에 붙이기 전에 정해야 할 운영 규칙

## 문제 상황

AI 도구 사용법은 많지만 실제 제품 제작 과정에서 어디까지 맡기고 어떻게 검수해야 할지 모른다. 나 역시 웰니스 앱 MomentTune의 MVP를 Claude Code와 역할별 AI 에이전트로 만들면서 같은 문제를 겪었다.

처음에는 에이전트를 많이 나누면 속도가 자연스럽게 올라갈 거라고 생각했다. 실제로 커밋, 화면, 결정 기록은 빠르게 쌓였다. 하지만 곧 더 중요한 문제가 보였다. AI가 코드를 만들어내는 속도보다, 사람이 그 결과를 믿고 받아들일 수 있는 구조를 만드는 일이 더 어려웠다.

## 왜 이 작업을 시작했는지

MomentTune과 SuriBlog 자동화 작업에서 직접 겪은 판단, 실패, 수정 과정을 연결한다.

## 실제 사용한 방법

Claude Code를 기본 환경으로 두고, 저장소 안에 세 가지 운영 장치를 심었다.

첫째, `.claude/agents/`에 역할별 에이전트 파일을 두었다. 각 파일은 프론트매터로 이름, 사용할 수 있는 도구, 모델을 지정하고 본문에는 역할과 가드레일을 적었다. `ceo`, `product`, `tech`, `recommendation`처럼 책임을 나누니 어떤 판단을 누구에게 맡길지 정하기 쉬워졌다.

둘째, `.claude/hooks/`에 실행을 가로채는 훅을 두었다. 중요한 규칙을 프롬프트에 부탁하는 대신, 특정 작업이 실행되기 전에 기계적으로 막거나 확인하도록 만들었다.

셋째, `.claude/skills/`에 반복 절차를 명령어로 고정했다. `/commit`, `/deploy`, `/new-screen`, `/engine-change`처럼 자주 반복되는 흐름을 매번 새로 설명하지 않고 같은 순서로 실행하게 했다.

그리고 `CLAUDE.md`는 긴 매뉴얼이 아니라 짧은 지도로 유지했다. "무엇을 알아야 하는지"를 길게 쓰기보다, 화면은 어디에 있고 결정 기록은 어디에 있으며 변경 전에 어떤 문서를 봐야 하는지 가리키는 역할만 맡겼다. 결정 근거는 `docs/DECISIONS.md`에 번호를 붙여 남겼다.

작업 흐름은 기능 하나를 기준으로 `research -> product -> ux -> tech/recommendation -> qa -> data -> business` 순서로 흘려보냈다. CEO 에이전트가 전체 우선순위를 조율하고, 매일 스탠드업 형태로 전날 진행 상황과 오늘의 우선순위를 정리했다.

다만 모든 것을 자동으로 넘기지는 않았다. 배포, 미뤄둔 기능을 당겨오는 결정, 외부 발신, 비용 발생, 자금 전략은 사람 승인 없이는 진행하지 않는 게이트로 못박았다. 그 외 일상 작업도 타입 체크와 테스트 통과, 그리고 파일 경로와 명령 출력 같은 증거 제시를 완료의 최소 조건으로 삼았다.

## 시행착오

프롬프트로 부탁한 규칙은 반복적으로 깨졌다. `.env`를 커밋하려 하거나, 손대면 안 되는 네이티브 폴더를 직접 수정하거나, 타입 체크 없이 커밋하려는 일이 생겼다. 그래서 기억이 아니라 기계로 막기로 했다.

`PreToolUse` 훅이 `git commit`을 가로채 `.env`, 타입 에러, 엔진 테스트 실패가 있으면 커밋을 거부하도록 만들었다. 네이티브 폴더 편집도 훅으로 차단했다. 규칙을 문장이 아니라 게이트로 바꾼 뒤에야 반복적으로 지켜졌다.

또 하나의 실수는 "완료" 보고를 곧이곧대로 믿은 것이다. 그래서 스탠드업 원칙을 "확인한 것만 완료로 쓴다, 근거 없으면 작업 내역 없음으로 쓴다"로 고정했다. 직접 확인하지 못한 항목은 확인하지 못했다고 명시하게 했다.

검증 전에 범위를 늘린 결정도 있었다. 상태 분류를 더 세밀하게 나누는 선택이었는데, 당시 내 권고는 "검증 후 세분화"였지만 실제로는 먼저 넓히는 쪽으로 진행했다. 옳고 그름을 떠나, 이런 판단을 결정 로그에 `맥락 -> 결정 -> 이유 -> 영향` 순서로 남겨두니 나중에 되짚기 쉬웠다.

가장 크게 막힌 건 코드가 아니라 자산이었다. 실기기, 개발자 계정, 백엔드 실 프로젝트처럼 사람만 열 수 있는 게이트 앞에서 코드 진전이 며칠 멈췄다. 이때 배운 건 "게이트가 필요한 작업"과 "게이트 없이 지금 할 수 있는 작업"을 처음부터 분리해두라는 것이다.

## 결과

결과물은 커밋, 화면, 테스트, 결정 기록으로 빠르게 쌓였다. 생성 속도는 사람 혼자 작업할 때보다 확실히 빨랐다. 하지만 진짜 성과는 코드 양이 아니었다.

더 중요한 변화는 AI에게 맡긴 부분과 사람이 쥔 부분의 경계가 저장소 안에 명시됐다는 점이다. 훅은 반복 실수를 기계적으로 막고, 승인 게이트는 되돌릴 수 없는 결정을 사람에게 돌리고, 결정 로그는 판단의 이유를 남긴다.

한 줄로 정리하면 이렇다. AI 에이전트 생산성의 병목은 생성이 아니라 검수와 신뢰다. 지키고 싶은 규칙은 부탁하지 말고 실행 가능한 게이트로 만들어야 한다.

## 독자가 적용하는 방법

1. 자신의 프로젝트에서 반복되는 작업을 하나 고른다.
2. AI에게 맡길 부분과 사람이 판단할 부분을 나눈다.
3. 초안, 검수, 발행 단계를 분리한다.
4. 작은 결과를 기록하고 다음 실험으로 연결한다.
